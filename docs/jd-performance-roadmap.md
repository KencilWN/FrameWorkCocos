# 棋牌小游戏性能岗位：学习偏向与验收路线

制定：2026-11-03（Asia/Shanghai）。依据：用户提供的《Cocos高级开发工程师（侧重性能优化）》JD截图及补充要求“搜索公开案例来教我，偏棋牌”。本文是当前方向调整；实际能力与完成情况仍只记在[progress](progress.md)。

## 1. 岗位要求与当前差距

JD明确写了“主导棋牌游戏客户端的性能瓶颈排查与深度优化”。职责覆盖FPS、内存与发热、首包与加载、DrawCall、长时间运行、性能规范及微信/抖音/支付宝适配；要求包括5年以上Creator实战、成熟小游戏优化案例、Profiler、GC、Spine，以及HTTP/WebSocket、断线重连和状态同步。WebGL/WebGPU/Shader、Native/C++、性能监控SDK和AI提效属于加分方向。

本科、工作年限和生产项目经历是招聘条件，当前未核实用户对应情况。课程能补能力和可复现实验，不能替代工作年限，也不把公开案例复述或自己的训练Demo写成参与过线上项目。

## 2. 主练习载体与边界

先收尾现有商店，再逐步新增一个**最小大厅→房间→牌桌展示→结算→返回大厅**的棋牌技术样例。第一版只需静态牌面、座位、头像占位和可控消息，不要求一次实现完整斗地主/麻将规则、完整后端或复杂AI。原商店保留，后续新场景/资源/Inspector绑定由用户实现。

练习围绕棋牌中具体的变化：

- 大厅/房间：首屏只加载所需资源，进房再加载牌桌；重复进退房检查监听、定时器、节点与资源持有。
- 牌桌：用固定手牌练重叠顺序、选中态、牌背/牌面/数字的渲染；固定牌数的牌桌先保持简单，不因为学了池或虚拟列表就强加它们。
- 列表与头像：大厅房间列表、排行榜、战绩采用可控数据量；头像可先用仓库内图片和延迟模拟，验证回收条目后旧结果不串人。
- 动效：出牌、发牌、表情或结算动效逐个加；比较常驻动画、按需播放、缓存模式与暂停/清理的成本。Spine素材需可用许可、版本适配并留在仓库。
- 对局恢复：回合制练习优先采用服务端权威状态、序号/版本和完整快照；客户端只发意图，不用本地扣金币示例冒充线上可信结算。实时动作游戏的预测/回滚不列为本轮前置。

## 3. 按前置能力推进

以下是学习顺序，不是固定每项一周。P项与K关并行记录：K1/K2保留原结论；K3不追加完整性能考核；K4～K8结合专项产出；原关卡通过不自动代表全部岗位要求通过。

| 顺序 | 前置/对应关卡 | 用户主要任务 | 必须留下的证据 |
| --- | --- | --- | --- |
| P0：业务收尾 | 当前K3 | 完成实验32，解释数量切换不重建列表、不写存档的原因 | 原成功/失败/重开验收；不声称两个数字切换已获得可测性能提升 |
| P1：工具与基线 | K3后、K4起 | 用原商店先录一次Performance/Memory；识别主线程任务、帧耗时、分配与保留对象；再用可控负载练定位 | 固定操作、设备/版本/构建说明、原始采样、一个有依据的假设；此时不强求优化收益 |
| P2：异步与内存 | K4～K5 | 先完成可控Promise/过期结果，再做头像延迟、重复进退房、共享资源加载释放与一次监听/定时器泄漏定位 | 开关前后保留对象/资源趋势和引用链；错误/关闭时状态正确；区分泄漏、缓存与峰值 |
| P3：渲染与动效 | K5～K6 | 学2D合批条件，做牌面/Label/头像排列对照；有测量需要时才改图集/层级；Spine增量加入并比较模式 | 同画面前后DrawCall、帧耗时及内存；遮挡、交互不变；不能靠减少可见内容冒充同等效果优化 |
| P4：列表与分配 | K6 | 独立比较直接创建、池复用、可视区域复用；数据可从30/300项起按设备调整，先证明问题 | 节点/创建次数、滚动帧耗时、分配和常驻内存；回收后不残留回调/选中态/旧头像 |
| P5：加载与包体 | K5～K7；微信初次导入可在P1后提前 | 做Web构建，再把样例导入微信工具；对比大厅/房间Bundle和按需加载，练冷/暖启动与加载失败 | 构建产物体积、请求与加载阶段、首个可交互时刻、峰值；分包不能让失败永远loading |
| P6：网络与恢复 | Promise/状态基础后，K6～K7 | HTTP成功/错误/超时；WebSocket连接状态、心跳、退避重连；房间版本、重复/过期消息与快照恢复 | 可控断线/重连日志；只保留一条有效连接和一组计时器；旧房间消息不改新房间、不重复结算 |
| P7：平台与回归 | K7～K8，贯穿P2～P6 | 微信真机验证，再做抖音/支付宝适配；长时操作与低/中端设备分级；独立完成一个性能问题闭环 | 分平台/设备记录、功能回归、优化前后报告及残余问题；热降频、功耗以工具实际可采项记录 |

P6先用仓库内可控传输替身训练顺序与失败，再补本仓库可启动的最小HTTP/WebSocket测试服务及锁定依赖；不借外部工作工程，也不把内置Native WebSocketServer当成Web/小游戏服务器。工具准备和业务练习分清责任，不在本轮提前写完整网络业务。平台API、HTTPS/WSS、域名、账号与权限要求在实际接入时查当时官方规则。

Web、开发者工具和各平台真机分开记录。缺少某平台账号、工具或设备时，记录首个阻碍并继续其他独立任务；该平台保持未验收。渲染/Shader路径需区分CPU提交、GPU负载与资源等待，工具看不到的指标标“未测”，不由FPS推算GPU耗时或发热改善。

## 4. 每次性能练习的做法

沿用“目标→成功/失败状态→反例→顺序→实现→验证”，增加性能证据：

1. 选一个可复现现象，固定数据、操作和画面。先记录基线，再提出原因假设。
2. 用工具找支持或推翻假设的证据；先定位主线程计算、资源等待、分配/GC、渲染提交等类别，不先套优化口诀。
3. 一次主要改变一个因素，保留原方案便于对照。用户决定方案并实现；助手按需给局部提示、解释官方案例和审阅。
4. 相同设备/版本/构建/分辨率/画质、相同操作长度对比；冷暖缓存分别测，记调试器/日志开关和预热。每种条件先至少3轮看波动，不能把单次结果当稳定结论。
5. 同时检查功能和成本：更快是否增加常驻内存、首包或首次加载；更省内存是否造成重载停顿。收益在噪声内就记录“未证明改善”。

学习阶段先说明30/60FPS等目标与帧预算的关系，再按设备基线定预算，不全设备硬套“必须60FPS/DrawCall低于N/提升30%”。平均FPS会掩盖长帧，逐步学习帧耗时分布/p95和卡顿位置；p95是帧耗时样本的95百分位，不是平均FPS换算值，样本量/时长也要保留。

内存分JS堆、引擎资源、纹理/GPU或平台总量分别记录；JS堆快照不能证明全部纹理/Native资源已回收。重复操作稳定不等于绝无泄漏，需要结合保留对象和引用链；池化降低分配可能增加常驻内存。DrawCall变少也需验证帧耗时和画面，不能直接推导一定更流畅。[Chrome堆快照说明](https://developer.chrome.com/docs/devtools/memory-problems/heap-snapshots)与[Creator资源释放说明](https://docs.cocos.com/creator/3.8/manual/zh/asset/release-manager.html)用于核对工具/引擎边界。

每份报告可用下列空白模板，数据实测后填写：

```text
题目 / 日期 / 本人完成与帮助程度：
现象、目标与失败时应保持的状态：
设备 / 系统 / 引擎 / 平台基础库 / 构建模式 / 分辨率：
数据量 / 固定操作 / 时长 / 冷暖缓存 / 预热 / 采样轮数：
工具及原始记录位置 / 调试器与日志开关：
基线 / 假设 / 定位证据 / 被排除的原因：
本次唯一主要改动 / 备选方案与成本：
前后数据及波动 / 功能回归 / 仍未验证项：
是否有改善 / 适用条件 / 下次回归的触发条件：
```

## 5. 案例教学与作品证据

已开始建立[公开案例研习库](guide/performance-cases.md)，包含有数据的公开报告、官方机制指南和引擎缺陷记录，明确它们的证据等级与版本。找到棋牌具体产品的第一手复盘再补；通用机制映射到棋牌时明确是教学推演，不冒称原文就是某棋牌产品实战。

每个案例先由助手解释“现象→证据→原因→方案→代价”，再由用户在本工程做一个最小复现与独立变式，最后写自己的对比报告。原文代码/素材不整体搬进仓库；确需引用先确认许可与版本，仓库已有只读快照保持不变。

目标逐步形成三类**训练案例**：进退房泄漏定位、牌桌/大厅渲染与列表卡顿、首屏/加载峰值；再补重连与状态恢复可靠性记录。完成数目不是授予高级能力的标准，面试说明需区分“阅读他人案例”“本人复现”“本人独立定位”“真实线上交付”。

## 6. 时间和取舍

原4～6学习周、15～23剩余学习日是原基础路线的历史预算，未包含本次岗位专项。新增Profiler、渲染、网络、多平台和长时验证需要额外投入，不挤成原工期的高级岗位达标承诺。先观察接下来的2～3次实际学习（数量选择收尾、首次基线、异步最小实验），再用真实耗时重估。

当前保留TS、业务正确性、异步和资源所有权；减少重复UI搭建和整套框架搬运。池/可视区域列表的诊断与取舍升级为必修，完整高通用虚拟列表框架仍非前置；复杂MVVM、泛型体系、全局管理器、队列与音频全功能后置。但棋牌短音效的生命周期与重复播放问题可纳入小案例。Shader/WebGPU、Native/C++和监控SDK后置，AI用于查资料/生成实验候选/审阅，结论仍以本人理解和实测为准。

最近顺序不变：**先实验32；再现有商店性能基线；再Promise/过期结果；之后渐进建立棋牌样例。** 本轮是计划与资料调整，没有新增业务实现、性能采样或能力过关。
