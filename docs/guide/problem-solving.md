# 训练从需求到实现的思路

目的是在选方案前先理解问题，避免凭第一感觉开写。不是给自己贴“浮躁/僵化”的标签，也不要求每个小改动写长文。新机制先留约5分钟分析，熟悉的一行修正可直接处理。

## 动手前四行

```text
目标：用可观察的行为描述，不先写技术方案。
成功/失败后状态：分别列哪些变化、哪些不变。
直观方案与反例：先提出简单做法，再找一个会违反要求的具体输入。
执行顺序：用人话说明检查、准备、提交、通知/保存的时机。
```

再问一个设计问题：谁拥有这份状态？这个功能需要协调哪些对象？如果全部放组件里，会让哪类变化相互牵连？当简单方案已经足够时，不必添加接口/基类。

## 当前恢复问题示范

目标是“根据外部记录恢复余额与背包”，并非“深拷贝snapshot”。导出快照是模型→普通数据；恢复是外部数据→经过检查的模型状态。

反例：原30金币/药水1，记录10金币/非法数量。若先reset真实钱包再加10，背包检查失败时原状态已破坏。

由“失败保持原状”推导“先不改真实状态”，再推导“准备候选钱包/背包，全部合法再替换”。`new Wallet(0,150)`不是要背的答案；完整检查余额后直接构造临时钱包也是可行方案。复用Inventory.tryRestore的理由是它已经负责物品校验与重建，避免另一套规则。

## 指定数量购买示范

初30买3瓶单价10应0/药水3，初25同请求应失败25/空。新参数不只影响入包，也影响扣款与退款。分析里写过总价仍可能在代码中漏掉，因此提交前把每项状态变化对应到实际执行语句。

不要逐次买3次来冒充“一次买3件且全成或全败”：初25可能买成2件，违反要求。

购买失败与保存失败分开：前者不改变模型/不保存；后者已成功购买，保留内存/UI、报告未持久化。本练习没有服务端资产事务。

## 卡住时定位哪一层

| 卡点 | 下一动作 |
| --- | --- |
| 说不清成功/失败应怎样 | 用具体数字列输入与输出；缺需求就明确标出来 |
| 不知道现成模块能做什么 | 打开该类，先看public方法/返回值/失败副作用，不重写一遍 |
| 顺序有争议 | 用一个“后一步失败”的反例逐步推演真实状态 |
| 不知道TS表达法 | 在最小例子查语法，不把整道题同时硬想 |
| 写完能跑但不确定 | 检查成功、失败、边界，以及变更涉及的所有数据 |

连续改动没进展时暂停补代码，回到“当前违反哪条要求”。先形成能解释的局部判断，不以打字速度评价设计能力。

助手先审阅思路，再给按需要缩小的提示；不会每次先把完整设计写完再让学习者填空。生成的框架基础设施可供读/用，但它的存在不计作独立能力。
