# 后续实操路线与验收

2026-11-03按[棋牌性能岗位](../jd-performance-roadmap.md)调整。业务/生命周期基础继续保留；Profiler、资源内存、渲染、列表、加载、网络和平台逐步加强。代码备齐、公开案例读懂或计划写好都不算实操完成。先按[问题求解流程](problem-solving.md)分析，由学习者实现和运行，助手解释机制与审阅。

## 立即继续：数量选择（K3 / P0）

按[实验32](../32-shop-quantity-selector.md)：界面切换1/3、显示当前数量，切换不改资产不保存；商品按钮使用点击当时数量。价格明确标单价，重开数量1但资产恢复。当前源码仍buyNum=2，尚未实施。

验收临时独立key首次30/空→多次切换不改资产→3瓶药水0/potion3→重开0/potion3且数量1→不足拒绝。结束恢复原key。用户亲手绑定节点并解释选择归页面、交易规则归模型；不为这两个数字切换增加池/性能框架或宣称已经提速。

## 接下来：现有商店的工具基线（K4 / P1）

先看懂一次测量，不立刻改业务。固定启动、点击、显示/关闭等操作，记录Creator/浏览器版本、分辨率、数据量、缓存与日志开关，采一份Chrome Performance记录与Memory快照。学习主线程任务、帧耗时、分配与保留对象的含义，指出一个需要进一步验证的原因假设。

原3商品负载未必存在性能问题；没有问题就保留基线。需要练工具时再在独立练习载体增加可控负载，不把人为放大的实验当产品故障。[案例C06](performance-cases.md)先教如何区分首屏可见与真正可交互，具体改造等待前置。

## 异步有效期→最小棋牌样例（K4 / P2前置）

先用可控Promise做A慢B快、关闭后返回、失败结束，再自行用LatestRequest比较直接刷新方案；解释忽略结果与取消工作的差别。尚无实际用时，原2～3次实操估计只作基础参考。

基础通过后渐进建立大厅→房间→牌桌展示→结算→大厅；第一版用静态牌面/座位/头像占位和可控消息。暂不要求完整棋牌规则、后端、复杂AI。将旧头像晚返回到已复用条目、上一房间结果污染下一房间作为变式；旧商店保留。

## 资源持有与进退房内存（K5 / P2）

在仓库准备可许可的小Prefab/图片，读本地ResourceLoader加载与结束入口，再接ResourceScope。验证正确/错误路径、加载前关闭、两处共享关闭一处不破坏另一处、消费者结束后归还。节点实例、Prefab、SpriteFrame、scope分别指定负责人。

结合[官方指南C02与动物餐厅C05](performance-cases.md)，将共享资源反例改成大厅/牌桌共用头像或图集。重复进退房观察保留对象/引用链及可测的资源趋势；分清泄漏、缓存、加载峰值与未观测内存。Node替身计数只能辅助，不替代实际引擎/平台结果。

一个小组件可在这里接ScopedComponent，用来比较手写on/off与scope；不一次重构全部旧课。PanelHost只用于真正需要的结算/奖励节点，模板资产另行持有。继承、super和共享资源结束顺序需能解释。

## 2D渲染、牌面与Spine（K5～K6 / P3）

先学图集、纹理/材质、节点顺序、Label和Mask怎样影响批次，再做同画面对照；用牌面/昵称/头像/分数组织练习，不盲目打破遮挡与点击关系。[案例C01](performance-cases.md)用于讨论DrawCall降低后剩余卡顿为何还在。

同时记录DrawCall、帧耗时和内存；看不到GPU耗时就不声称GPU优化完成。Spine在静态牌桌稳定后单独加入，比较同屏数量、实时/缓存计算、皮肤/事件需求与内存的代价；素材版本与许可先核对。旧2.x改引擎/静态合批方案不直接套3.8.7。

## 列表、池与GC（K6 / P4，由选修改为专项必修）

用大厅房间列表/战绩列表扩充可控数据，先测全量创建与滚动，再由用户比较分帧、池或可视区域复用。牌桌固定少量牌不必强行虚拟化。[案例C04](performance-cases.md)练把经验变成待测假设。

验收节点/实例化次数、帧耗时与分配/GC、常驻内存和首次完成时间；回收后旧文字/选中态/头像/回调不串扰。基本可视区域复用与成本判断必修，完整泛用列表框架和整套原版算法移植不作为前置。不能把池中保留的节点都算泄漏，也不能把对象变少自动等同更快。

## 包体、首屏与平台起步（K4～K7 / P5）

先完成Web构建，在真实浏览器跑；随后尽早把基线导入微信开发者工具，不等所有模块学完。待资源前置通过，再对比大厅/房间Bundle划分、共用依赖、首场景范围与按需加载。按[首屏案例C06](performance-cases.md)分别测主包/总包、下载/解析/创建、首屏出现与首次可交互，以及冷暖启动和峰值内存。

微信先形成开发者工具与真机各自证据，再把相同样例接到抖音/支付宝验证差异。账号、域名、权限、包体限额与可用分析能力在接入时核对官方当时说明；条件不足记首个阻碍和未验项，继续其他不依赖它的任务。

## HTTP/WebSocket与牌局恢复（K6～K7 / P6）

异步与状态基础通过后，从HTTP成功/错误/超时→WebSocket连接/关闭→心跳/退避重连→房间快照与增量消息逐步练。先用可控传输替身练乱序与失败，再补仓库内可启动的最小测试服务及锁定依赖；不借工作项目服务器，也不把Native内置WebSocketServer当Web平台服务器。

回合制练习采用服务端权威可见状态；明确房间/局次、状态版本和请求标识。断线后先恢复有效快照再应用后续消息，旧房间/旧版本不覆盖新状态，重试/重复消息不重复结算。计时器以服务端截止时间等契约恢复，不盲目补播全部历史动画。具体协议由用户先分析，不预发完整业务实现。

验收快速进退房、网络中断/恢复、重复/迟到消息、关闭清理；只有一条有效连接和一组对应计时器。模拟结果、本地真实传输和平台弱网分开记录，不把本地钱包数据当可信线上资产。

## 第二使用场景、规范与独立交付（K7～K8 / P7）

保留奖励页或结算页复用需求，重新决定共享玩家状态持有者。简单ObservableValue/手工事件先比较通知入口；复杂MVVM、泛型体系不抢占诊断和独立任务时间。队列、音频全功能按需要选修；棋牌短音效可用[案例C03](performance-cases.md)练重复播放与资源责任。

独立做一个1～2小时范围可控的功能或局部定位题；完整性能案例含反复采样可能另需时间，不强塞进编码估时。报告保留现象、原因证据、改动/替代、前后数据、功能回归与局限。逐步积累内存、渲染/列表、加载三类本人训练案例，以及网络恢复记录。

长时练习可从30分钟及固定进退房次数起步，记热状态、平台模式、设备和中断；收益需同条件至少3轮观察波动，无法采功耗/温度就保留未测。沉淀一份从本人案例得到的性能检查清单和预算，再用于第二个需求回归，不先造监控SDK。Web、微信、抖音、支付宝与不同设备分别验收，K8和全部P项都不等同高级岗位/生产规模能力。

## 时间与恢复

原4～6学习周/15～23剩余学习日仅是基础路线历史预算，不含新增专项。接下来2～3次任务记录分析、编码、调试、采样和帮助程度，再重估。只后置复杂框架与加分项，不删除核心业务正确性、所有权、性能取证和失败路径；实际进度始终见[恢复点](../progress.md)。
