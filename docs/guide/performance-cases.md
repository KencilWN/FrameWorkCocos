# 棋牌方向：公开性能案例研习库

建立/核对：2026-11-03。当前仅完成资料筛选，以下实验均**未由学习者实施或验收**。方向与前置见[岗位路线](../jd-performance-roadmap.md)，实时进度见[progress](../progress.md)。

JD明确是棋牌客户端。当前筛选到的资料中，有通用小游戏测量报告、官方指南和引擎缺陷记录；不能把它们都称为已公开的某款棋牌产品复盘。选材优先原发布者、引擎官方、官方仓库；商业供应方数据标明身份，不当作独立验证。案例分“原文事实”和“本工程教学映射”，映射不是原作者结论。

## C01：DrawCall大降，为什么帧率没有同比大涨？

来源：[多纹理合批3.x（性能狗测试）](https://forum.cocos.org/t/topic/161527)，Cocos社区2024年帖子，发布者为插件作者“我是98k”；文中称测试数据由用户公司的上线项目提供，产品名称与类型未公开。是供应方发布的项目对比，不是Cocos官方背书，也不是学习者复测结果。

**原文可核对事实：** Creator3.8.x、微信高性能模式、iPhone12、30分钟测试。报告DrawCall约120→30，中位FPS 50→53，卡顿时长占比8%→5.7%；仍有动态创建造成的卡顿，作者提出继续处理加载/创建。没有原工程和完整原始采样，不能独立确认全部因果或认定游戏类型。

**教什么：** 减少提交批次可能改善一部分开销，剩余瓶颈仍需定位；DrawCall比例不能直接当FPS提升比例。先用[3.8合批规则](https://docs.cocos.com/creator/3.8/manual/zh/ui-system/components/engine/ui-batch.html)检查材质、纹理、层级与Mask等条件，而不是先买插件/改引擎。

**棋牌教学映射：** 自建大厅房间列表或牌桌，把牌面、昵称、头像、分数穿插显示；只改变一个合批因素，保持遮挡与点击结果一致。先预测批次变化，再看DrawCall、帧耗时与内存。若负载太小测不到收益，保留“未证明提速”结论；后续独立变式加入一个Mask或频繁变化的Label，解释结果是否仍成立。

**前置与交付：** P1工具基线、P2基本生命周期之后进入P3；交一张同条件前后表、一段定位证据、一个未解决问题。此课不要求实现多纹理合批器。

## C02：JS堆不大，为什么iOS小游戏仍可能内存吃紧？

来源：[Cocos官方技术支持团队：iOS微信小游戏内存与性能优化指南](https://docs.cocos.com/creator/3.8/manual/zh/editor/publish/wechat-ios-optimize.html)。这是机制/排查指南，**不是某款棋牌产品的前后对比案例**。

**原文可核对事实：** 指南区分脚本、音频、字体、图片与Canvas等内存来源，并讨论高性能模式、图像缓存及纹理策略。文中历史设备阈值、平台开关及性能数字不可直接当作2026年所有机型的保证；实际接入还需核对平台当时说明。

**教什么：** 先问测的是哪一层内存，再分析资源持有、峰值和缓存。需要同时参考[Chrome堆快照](https://developer.chrome.com/docs/devtools/memory-problems/heap-snapshots)与[引擎释放规则](https://docs.cocos.com/creator/3.8/manual/zh/asset/release-manager.html)，不能只凭JS快照下降或调用decRef就宣称全部资源释放。

**棋牌教学映射：** 大厅→房间→结算→大厅重复操作，观察头像、牌桌背景、字体与音效的持有。先用仓库内小素材固定负载，主动保留一条监听或图片引用做最小故障，再由用户找引用链并修正；记录相同操作轮次的趋势。单纯一次峰值上升不直接判泄漏。图集减少切换也可能让大厅持有整张牌桌图集，需要比较内存与重载停顿。

**前置与交付：** P2实际资源加载后使用；交内存分类、一个保留链证据、修复前后重复操作记录。无iOS设备时浏览器实验单独验收，iOS保持待验。

## C03：音效播放后内存增长，如何形成最小复现？

来源：[cocos-engine issue #14017：WeChat mini-game audio memory growth](https://github.com/cocos/cocos-engine/issues/14017)，2023年报告，原报告环境为Creator3.6.2，关联复现材料；当前页面状态Closed、里程碑V3.8.1。**关闭状态本身不能证明3.8.7上的所有音频增长已修复。**

**教什么：** 保留版本、运行环境、复现步骤、次数和测量口径；先分清业务持有、缓存及引擎/平台差异，再判断是否需要查引擎缺陷。它是缺陷报告，不是有完整修复收益的优化案例。

**棋牌教学映射：** 发牌/出牌短音效、连续表情音效，比较不播放、单次、固定次数重复播放和释放后的趋势；素材本地自备且有许可。分别检查Source/Clip/回调持有，不机械照搬旧版补丁，也不通过每次都加载音频来人为制造产品结论。

**前置与交付：** 已理解资源所有权且确需音频时使用；交一个本仓库可复现条件、版本差异表、实际观测与未验证范围。无需为了复现旧缺陷降级主工程。

## C04：分帧与对象池为什么也可能有代价？

来源：[小游戏性能优化分享](https://forum.cocos.org/t/topic/138886)，2022年，作者自述来自“欢乐互娱”，发布于Creator2.x分区。属从业者经验分享，列出池缩容、资源卸载、列表复用、分帧等思路；缺少足够统一的测试环境和前后数据，不能视作本工程已验证的最佳方案。

**教什么：** 把经验转成可证伪假设：池是否增加常驻节点；分帧是否延长可交互等待；截图背景是否增加纹理和截屏成本。原帖部分技巧在回复中有争议，不能作为无条件口诀。2.x API或引擎修改不直接搬进3.8.7。

**棋牌教学映射：** 大厅房间列表比较全量创建、分帧创建与可视区域复用，交互和加载完成契约保持一致；牌桌固定数量小对象先保持直接实现。用卡顿、总完成时间、峰值/常驻内存同时判断，暂不实现泛用复杂列表库。

**前置与交付：** P4列表实验；交一次方案比较、一次回收状态错误的定位记录，及何时不值得使用池的解释。

## C05：《动物餐厅》：页面仍在加载，共享图片却被释放

来源：[动物餐厅项目内存优化思路分享](https://forum.cocos.org/t/topic/98999)，2020-10-14，作者以项目开发者口吻分享，Creator2.0.10/JavaScript；正文页面抓取超时时已通过同站主题JSON核对。是项目经验自述，有低端机崩溃率变化图；非棋牌，也不是本人的独立复测。

**原文可核对事实：** 文中讨论资源按需加载/释放，以及Home、Garden共用图片时，一方释放而另一方尚未完成加载的错误；加载过程的保护与失败清理也需考虑。旧cc.loader及项目自建引用规则不能直接搬到3.8.7。

**棋牌教学映射：** 大厅与牌桌共用一张本地图集，制造“进房加载未结束就退出大厅/切到另一房间”。由用户先列已显示消费者、加载中请求、缓存和资源各自的责任，再比较“常驻共享资源”“每个消费者显式持有”“加载期间单独保护”的适用条件与内存成本。实际行为以3.8.7资源机制验证，不先假定旧缺陷仍存在。

**前置与交付：** P2真实资源加载之后；交时序、失败后状态、共享不误释放的实际结果及重复操作的内存证据。不照搬原项目禁止某些节点API的内部规范。

## C06：SmallMain：首屏渲染快了，玩家是否更早能操作？

来源：[Cocos Creator微信小游戏平台启动与包体优化](https://forum.cocos.org/t/cocos-creator-50/94999)，2020-07-01，作者SmallMain，Creator2.4，文中声明测试数据来自微信云测试；已用同站主题JSON核对。是一手工程实验，非棋牌，旧构建模板不是当前工程的实施方案。

**原文可核对事实：** 文章分别讨论首屏呈现、引擎加载与包体拆分，并提醒首屏呈现改善不等同实际加载流程全部加快；部分延迟执行思路作者明确注明未测。标题中的约50%效果属于文内特定云测条件，不能当作我们的预期收益。

**棋牌教学映射：** 自建三个可观察时刻：加载画面出现、大厅所需数据/资源完成、房间按钮首次可用。用户比较最小大厅先启动与一次加载全部房间两种方案，并检查资源失败能否结束等待。把“先显示进度画面”与“真正更早进入牌桌”的收益分开，不以提前显示静态图片完成整条启动优化验收。

**前置与交付：** P1先理解指标，P5构建/加载时实验；交冷暖缓存与请求阶段、主包/总包体积、可交互时间和峰值的对照。具体Bundle/平台构建选项按3.8.7及当时平台文档核对。

## 每轮怎样上课

1. 助手在聊天中给出当轮完整必要内容，先讲原文事实、版本、缺失证据与本次待验证假设，不要求用户先读完全部链接。
2. 用户写目标、成功/失败后状态、反例、执行顺序；预测一个现象。工具首次操作可示范，关键业务/实验变式由用户实现。
3. 同条件采样→定位→小改动→复测→功能回归；没有收益或假设被推翻也可以完成一次有效排查。
4. 分别记录他人报告、助手解释、用户复现与独立变式；个人作品只写自己实际做过的部分。
