## 目标与边界

买药水/宝石后停止重开，余额和道具作为同一份记录恢复。使用新key framework-demo.shop.snapshot.v1，与旧钱包和A/B背包键分开；旧InventoryPanel继续禁用。ShopModel生成/验证快照，ShopPanel协调存储调用，LocalStorage复用现有JSON封装；不把余额和背包拆成两次独立写入。

快照是普通数据对象，包含同一时刻的余额与背包记录。单键一份JSON避免调用方分两次写入只成功一半，不据此声称实现了通用崩溃恢复或分布式事务。

## 写代码之前：为什么这样设计

### 从变化判断边界

目标不仅是关掉预览还能恢复。还要保证换布局不会改购买规则、损坏背包不会只恢复余额、存储工具不写死商店字段。也要承认当前只有一个小商店，不提前引入完整服务层、仓储接口或继承体系。

| 当前设计 | 解决的问题与收益 | 代价、替代和升级时机 |
| --- | --- | --- |
| ItemConfig保存名称/价格，InventoryItem保存ID/数量 | 商品定义与玩家拥有量分开，调价格不用重写每条背包记录；ID负责关联 | 展示需查询配置并处理找不到ID；当前三条线性查找足够，量大且高频再比较索引。若需保留历史成交价，应新增订单字段，不能期待当前配置还原历史 |
| ItemCell只显示和报告点击，通过回调把决策交给页面 | 不引用具体ShopPanel，另一个页面可传不同处理函数 | 每个格子的闭包有对象分配和引用持有成本，持久保留格子回调也可能延长页面存活。三条无性能证据需优化；大量列表先检查创建/复用与生命周期 |
| ShopModel组合Wallet和Inventory，tryBuy协调一次购买 | 钱包只负责余额规则，背包只负责物品规则，购买成功/失败由一处协调；可脱离界面测试业务 | 多一个类和调用层；当前仍依赖具体配置查询并自行创建钱包/背包，不是任意游戏即插即用的服务。第二页面共享同一玩家状态时需调整持有者/传入依赖 |
| ShopSnapshot为普通数据契约 | 明确保存coins/items，避免存入Node、监听、类内部字段；调整实现时可保留存档结构 | interface在运行时不存在，不校验JSON也不加速；type也可表达此结构。字段变化仍需版本/迁移方案，现阶段不预建完整版本系统 |
| getSnapshot与getItems复制数据 | 调用者整理或修改导出对象不会绕过模型规则改真实状态；当前字段皆为基本值，逐条复制足够 | O(n)时间与对象分配，频繁调用会增加垃圾回收负担；在保存时调用合理，不应无理由逐帧复制。readonly不等于运行时隔离，嵌套对象加入后要重新评估复制深度 |
| tryRestore先准备候选数据，全部合法后替换 | 对当前同步调用，失败时真实余额/背包都不变；复用Inventory自身校验，避免另一套物品规则 | 需要临时Inventory及复制内存；比就地写入成本高。大数据需评估内存峰值；并发、异步与通知副作用需另行设计，当前不具备通用事务能力 |
| ShopPanel协调loadShop/saveShop，LocalStorage只做JSON读写 | 通用工具不认识商店key和业务字段，ShopModel不决定存储平台，刷新函数不偷偷写盘 | 目前页面承担一定协调；同逻辑多个页面使用或增加云存档时再抽持久化协调层/适配接口。现在为唯一调用点加整套接口会增加理解与维护成本 |

### 为什么是这些函数、接口和文件

- `getSnapshot`是向外导出状态的明确入口；`tryRestore`是从外部输入进入可信内存的检查入口。两者用途和失败责任不同；不直接公开wallet/inventory供任意修改。
- `saveShop/loadShop`管理读写时机、key及失败提示；`refreshShop`只负责显示。这样调整显示次数不会连带覆盖存档。函数需要独立职责，不只是把长代码切碎。
- `ShopSnapshot`声明成功时的数据形状；`unknown`描述尚未验证的外部输入，两者不矛盾。JSON可被旧版本或临时代码写入，`as ShopSnapshot`和`any`都不会检查它。
- Wallet、Inventory、ShopModel拥有不同规则和变化原因，所以各有脚本。ShopSnapshot目前放ShopModel同文件就足够；当多个模块独立使用它时再考虑单独文件。拆文件本身没有运行时提速收益。
- ShopModel“有一个”Wallet和Inventory，不“是一种”Wallet。这里使用组合；让ShopModel继承Wallet会暴露直接加扣钱入口，绕过购买协调，并且不能据此同时继承Inventory。真正有可替代关系、稳定共性时才考虑业务继承；引擎组件继承Component是参与引擎机制的另一种需求。

### 当前方案的诚实边界

ShopModel是教学业务模型，不是迁入的通用框架。它目前仍有未使用的cc模板导入、硬编码150、具体配置查询，以及只能表达成功/失败的boolean返回。去掉模板导入可让源码依赖更清楚；不要把未使用导入说成已产生确定的运行开销。需要区分余额不足/配置错误给UI不同提示时，再讨论带原因的结果类型。当前同步退款也不是通用支付事务。

单份快照是本练习选择的一致性单位。若余额以后还被奖励页消费，应先确定玩家状态的共享负责人，不能让每个页面各建一个钱包和各存一份余额。是否合并存档要看真实数据所有权，而非永远“一页一个key”。当前只演示离线单页面购买，不提供真实支付或服务端资产可信性。

运行检查继续使用后文原流程。设计检查只结合一个变化讨论：如果新增奖励面板领取potion，它可复用Inventory、配置及通用读写；不应调用tryBuy冒充领奖，因为领奖没有扣款。当前私有背包无法自然共享，需重新决定模型持有者。能指出这一限制，比为了未来先写一个庞大通用基类更有价值。本轮不实现奖励页。

## 1. ShopModel由用户实现

在ShopModel.ts类外导出接口：

```ts
export interface ShopSnapshot {
    coins: number;
    items: InventoryItem[];
}
```

新增public getSnapshot(): ShopSnapshot，返回新对象：coins来自现有余额，items使用现有getItems副本；不保存配置名称/价格或直接返回内部数组。

新增public tryRestore(data: unknown): boolean，任意失败都保留调用前的钱包和背包，合法时整体替换：

1. 输入是非null、非数组的对象，否则false。
2. 按已学方式读取字段：const row = data as { coins?: unknown; items?: unknown }。不直接as ShopSnapshot跳过检查。
3. coins必须是number、整数、0～150（含两端）；0是有效余额，不能用if(row.coins)筛掉。
4. 创建临时Inventory，将row.items交给它的tryRestore；失败false，真实模型不变。
5. 所有验证通过后才用new Wallet(row.coins,150)替换this.wallet，并用临时背包替换this.inventory，返回true。可将150提成共用成员，非必需重构。

不要在背包校验之前替换真实钱包，否则遇到“余额合法、背包损坏”时就恢复了一半。恢复直接采用验证后的余额/记录，不重新执行tryBuy。

## 2. ShopPanel由用户接入

从../../Framework/storage/LocalStorage导入LocalStorage；模块级常量const SHOP_STORAGE_KEY = 'framework-demo.shop.snapshot.v1'；类内private storage = new LocalStorage()。现有private shop = new ShopModel(30)保留，提供缺失/损坏存档的默认状态。

- private loadShop(): void：读取saved；null只return；否则shop.tryRestore(saved)，false提示“商店存档无效，使用默认状态”。不自动保存或删除旧记录。
- private saveShop(): void：storage.setItem(SHOP_STORAGE_KEY, shop.getSnapshot())，返回false提示保存失败，内存购买和界面继续，不回滚已成功的内存购买。
- onLoad必要引用检查通过后调用loadShop，早于start的首次refreshShop。
- handleBuy仅成功时保存并刷新；失败不写存档。沿用现有同步成功分支，不强制刷新/保存顺序；保存失败不能阻止刷新。
- refreshShop仍只显示，不读写存档。LocalStorage已有stringify/parse，页面直接传对象。

原场景/两个Label/Prefab与回调不需要增加绑定。新key首次为空，初始30/空是预期。

## 4. 坏背包结构不能只恢复余额

临时在onLoad中、this.loadShop()之前注入：

```ts
this.storage.setItem(SHOP_STORAGE_KEY, {
    coins: 0,
    items: [
        { itemId: 'potion', count: 8 },
        { itemId: 'gem', count: -1 },
    ],
});
```

预览应提示无效，显示默认30/空；不能变成0/空或残留药水8。0余额合法，失败源于后面的背包记录；验证延迟提交两个状态。

验证后删除注入、保存并重新预览。坏记录仍在，继续默认30/空是预期；点击药水一次→20/potion1，成功保存新快照，停止重开应仍20/potion1。结束不遗留注入，配置保留三条10/20/5。
