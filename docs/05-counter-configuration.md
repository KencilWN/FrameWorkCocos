# 实验五：同一脚本，不同配置

前置：用户已修正上限判断，计算候选值后校验，再提交并通知；145、148、150三组边界均报告通过。

目标：把初始余额、每次增加量与上限变成组件参数。左右两套计数器仍使用同一个 CoinCounter 类，由各自组件配置决定差异。本轮由用户自己修改脚本与 Inspector，不预先改资产代码。

## 1. 新增三个配置字段

在 CoinCounter 类中添加三个数字字段，并使用 @property 暴露到 Inspector。已有 import 与 const 解构已经提供 property，无需另加导入。

第一个示例：

```ts
@property
initialCoins: number = 100;
```

其余两个照这个写法自己声明：

| 字段名 | 类型 | 代码默认值 | 含义 |
| --- | --- | --- | --- |
| initialCoins | number | 100 | 新实例的初始余额 |
| addStep | number | 5 | 每次尝试增加的数量 |
| maxCoins | number | 150 | 余额上限 |

这里@property登记的是可编辑/序列化属性，数字字段可根据默认值识别其类型；先前的@property(Button)额外明确字段接收Button组件引用。保留原来private coins运行字段，不把它改成配置字段。

## 2. 把规则接上配置

自己找到并替换这些固定数字：

- start 中测试用的148，改为读取 this.initialCoins。
- addCoin 中固定的增加量5，改为读取 this.addStep。
- addCoin 中固定的上限150，改为读取 this.maxCoins。

保留候选值→判断→提交→emit的结构；清零仍只把this.coins改成0，不修改initialCoins。onEnable继续显示当前余额，不重新赋初值。

## 3. 配置两套实例

保存脚本，等待Creator导入。分别选中CoinCounterL/R，在各自的CoinCounter组件填写配置，再保存场景。

| 实例 | Initial Coins | Add Step | Max Coins |
| --- | --- | --- | --- |
| CoinCounterL | 100 | 5 | 150 |
| CoinCounterR | 10 | 3 | 20 |

把两边增加按钮的固定文案改为「增加」，避免右侧实际加3而仍写Add 5。暂时使用手动文字，后面按需要再做动态文案。

这三个字段属于各自组件实例，修改右侧配置不会改左侧；Inspector的已保存值在场景加载时恢复，不必复制一份脚本写另一套规则。

## 4. 运行验收

刷新预览：

- 左侧初始100，点两次为110。
- 右侧初始10，依次点击应为13、16、19；再点一次会超过20，拒绝，保持19。
- 清零右侧后再增加为3。
- 左侧隐藏/恢复保留当前余额。
- 两套互不影响。

本例采用拒绝整次增加的规则，右侧不会把最后一次3自动改成1来补到20。提示文案可改为「本次增加会超过上限」，更准确描述未达上限但下一步会越界的情况。

## 5. 本轮要解释的区别

- initialCoins：决定创建后从哪里开始的配置。
- coins：运行过程中随操作变化的状态。
- addStep/maxCoins：决定允许怎样变化的规则参数。

把变化参数留给各实例配置，稳定流程留在同一个类中，是一项小范围复用设计。后续还要独立讨论非法配置、状态所有者和存储，当前按表中的有效参数验证。
